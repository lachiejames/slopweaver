# 9 · Holding the current system up against all of that

Part of [What the owner wants from the corpus — harvested from the owner's own voice](../corpus-intent.md).

What follows is a keep/change/drop judgment on each piece, with the harvested intent that decides it. The
verdict column is about **fit to stated intent**, not about code quality.

## The retrieval pipeline

The owner's retrieval ruling ([hard constraint 1a](../constraints/hard.md#1a-retrieval-is-postgres-full-text-over-the-store-nothing-else))
settles this axis: there is no BM25 or other locally-built index, no embedding or vector index, no reranker, no
fusion, no recency multiplier and no passage selector. A question reads Postgres full text through
`store read`/`store cite`, and a detective reads a whole shard and decides for itself what answers. Two pieces of the
owner's intent bind whatever reads:

| Piece                                 | Verdict    | The intent that decides it                                                                                                                                                                                                                                        |
| ------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Staleness reaches the answer**      | **STANDS** | The owner judges it probably correct not to name stale information. An old record must not be cited as if current; recency is a judgement the reader makes, not a score.                                                                                          |
| **The per-record budget in `distil`** | **CHANGE** | Each batch spends `DISTIL_RECORD_CHARS` (1,200) per record across its records (`src/gold/recordBody.ts`), and a clipped batch's brief says so. A computer that read half of every file would be a mess. Owned by `record-truncation-at-1200-chars-in-both-lanes`. |

## Things worth saying "this is not what the owner asked for" about

The owner asked explicitly for this section: the handover doc that commissioned this work instructs a
willingness to say this part is not what the owner asked for, and records that the owner asked for that
explicitly.

1. **A fixed pipeline where the owner described a dynamic one.** `ask brief` → compose → `ask answer` is a good
   shape for _one_ strategy. It is not the thing the owner has described on four separate occasions. This is the
   whole of Problem 2 and nothing currently owns it.

2. **The corpus as the only source in the answer path.** Every time the owner has been asked whether the corpus or
   live reads should answer, the answer has been "it depends on the question, and often both". The code
   makes that choice once, statically, for every question.

3. **Optimising the golden set against the wrong corpus.** Not wrong to have built it — wrong to keep
   treating its numbers as evidence about the work corpus.

4. **Reporting truncation instead of ending it.** The repo is scrupulously honest about the 1,200-char cut
   — stderr warnings, measured, tested. The owner did not ask to be told about it; the owner's point is that a
   computer reading half of every file is a mess. Honesty about a lossy read is a mitigation, not the fix, and
   `constraints/hard.md` §3 already says so.
