# What else can cmux do for a supervised fleet?

Live-tested on this machine against ~15 real running Claude Code sessions (see
`cmux tree --all`). Everything marked **measured** below was actually run, not read off `--help`.

## 2. The three tried live

### (a) `cmux events` as a subscription — works, and it's better than hoped

**Measured**: `cmux events --after 71872 --no-heartbeat --no-ack` against the retained buffer (4,096
events, `~/.cmuxterm/events.jsonl` on disk beyond that) returned, across ~15 live sessions in one
evening: 84 `agent.hook.Stop`, 16 `agent.hook.Notification`, 20 `agent.hook.SubagentStop`, 6
`agent.hook.SessionStart`, 2 `agent.hook.AskUserQuestion`, 1,174 `agent.hook.PreToolUse` — one event
per tool call, per session, with `session_id`, `cwd`, `workspace_id`, `tool_name`, and phase
(`received`/`completed`).

This is a real answer to "can the supervisor learn a session finished its turn / is waiting /
asked for permission, as it happens": subscribe with
`cmux events --category agent --name agent.hook.Stop --name agent.hook.Notification --name agent.hook.AskUserQuestion --cursor-file <path> --reconnect`
and each of those three states arrives as its own JSON line, filterable by `workspace_id` to one
session or left open for the whole fleet. `--reconnect` plus `--cursor-file` means a supervisor
process that dies and restarts resumes exactly where it left off — no replay gap, no double-count.

This is strictly better than the 20-minute sweep (§ 3) for the "did something change" half of that
job, and it is wired: `slopweaver cmux events` drains the stream from a resumable cursor or follows it live,
`slopweaver session watch` folds its hook events into one signal per session, and a supervisor's first sweep
reads `cmux events --name agent.hook.PreToolUse` as the witness that it invoked its own skill.

### (b) `diff --last-turn` — a rendered split, not a text primitive

**Measured**: `cmux diff --source last-turn` on this machine returned
`Error: browser_disabled: cmux browser is disabled` — an outright failure, not a degraded result.
`cmux diff --help` confirms why: every `diff` source (`--unstaged`, `--staged`, `--branch`,
`--last-turn`) "renders a unified diff or patch **in a cmux browser split**" — it is a UI-rendering
command with no text/stdout mode, and it hard-depends on the cmux browser subsystem being enabled
(`cmux browser status` → `disabled` here).

So `diff --last-turn` is not a "what did it just do" CLI primitive — even with the browser enabled, its
output is a rendered split for a human to look at, not something a script can consume. The lightweight
route for a locally-running session is `git -C <workspace-cwd> diff` directly (the cwd is already known
from `sidebar-state`/`workspace list --json`, and cmux exposes no diff **text** RPC method —
`cmux capabilities` lists no `*.diff` method at all). `sidebar-state`'s `git_branch` field already
tells you clean-vs-dirty cheaply as a pre-filter before paying for the actual diff.

### (c) `workspace status` + `todo` + `set-progress` — works, and Slopweaver writes none of them

**Measured**, on this session's own workspace: `cmux todo add "…" --state in-progress --origin
agent` then `cmux todo list` showed the item back immediately; `cmux workspace status set review`
then `cmux workspace status` showed `review` with `inferred: working` and
`override: review (auto-clears when inferred moves off working)`; `cmux set-progress 0.4 --label
"…"` then `cmux sidebar-state` showed `progress=0.40 …` back. All four read back correctly and
instantly through the exact same socket a completely separate process (or the supervisor) would
poll — no transcript read, no screen scrape.

**Nothing in Slopweaver writes them.** The owner's console ruling: the owner reads no sidebar checklist
or status lane, so a seat's state reaches the owner only as a Queue card or a floating note. `handover start`
publishes the row's `workspace:N` ref pill and nothing else (`src/handover/workspaceRefPublish.ts`).

## 3. Where each supervision job lands

| Job                                   | What answers it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Did a spawn boot, did its pickup land | `src/cmux/spawnPolling.ts` (boot), and `src/cmux/witness.ts`'s chain inside `pickupWitnessWindow.ts` (pickup). Boot: a `SessionStart` hook for the new `workspace_id`, then the rendered prompt, for up to `MAX_BOOT_POLLS` (15 ticks). Pickup: hook events, then `latest_submitted_message`, then a running turn (`esc to interrupt`), then the screen, with the composer read on every tick nothing answers, for up to `MAX_SEND_VERIFY_POLLS` (30 ticks), then 30 more after one re-submit — a string match on rendered chrome is the fallback, never the witness |
| A dispatch false negative under load  | `latest_submitted_message` is the independent witness for a screen that answers `Failed to read terminal text` on every tick. **It does not close the class**, MEASURED: a pickup QUEUED in the child's input raises no hook, can leave `latest_submitted_message` empty (workspace:398; populated at once on workspace:410 alongside it, so its ABSENCE proves nothing) and shows an idle prompt. So `src/cmux/spawn.ts` reports an `unwitnessed` delivery and never re-sends, and the ask lane records `dispatch-unwitnessed` rather than `dispatch-failed`        |
| A session's OS pid                    | `cmux top --processes --workspace <ref>` (`slopweaver cmux processes`), cross-checked live against `ps -p <pid>` — exact match, full command line including `--session-id`                                                                                                                                                                                                                                                                                                                                                                                           |
| Liveness, stuck, waiting              | The 20-minute `ScheduleWakeup` sweep (`skills/supervisor/SKILL.md` § 7) classifies on a fixed cadence; `cmux events` is the wake-on-signal half for these three (§ 5 item 2). The sweep keeps the parts events don't cover (§ 4)                                                                                                                                                                                                                                                                                                                                     |
| Talking to a session                  | `ListAgents`/`SendMessage` (Claude Code's own channel — a `from`/message, no session id, no host; `.claude/rules/cross-session-messages.md`) or `slopweaver cmux send`. cmux's events and status verbs tell you a session's **state**, never carry a message                                                                                                                                                                                                                                                                                                         |
| What a turn reasoned                  | Transcript reads under `~/.claude/projects` — nothing here replaces them (§ 4)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## 4. What cmux does not cover

- **The content of a session's reasoning.** Every mechanism above tells you a session ran a tool,
  finished a turn, or is waiting — none of them tell you _what it decided or why_. That is still
  only in the transcript (`~/.claude/projects/.../*.jsonl`) or a screen read. `Notification` events
  in particular are aptly named: they say "something needs attention," never what.
- **Diff content as text.** No `*.diff` RPC method exists (confirmed against the full method list in
  `cmux capabilities`); `git diff` against the known cwd is still the way to get it.
- **A supervisor↔session talk channel.** Events and status are one-way telemetry out of a session.
  Two-way coordination is still `SendMessage`/`ListAgents` (Claude Code's own mechanism) or
  `cmux send`/`send-key` (typing into the surface) — cmux adds no messaging primitive of its own
  beyond those. Neither channel is INTERRUPTING: a session mid-turn queues what arrives, which is why
  `slopweaver cmux send --interrupt` exists and why it is opt-in, and why `slopweaver cmux stop <workspace>
--why "…"` stops what a peer seat is doing without waiting for it.
- **Automatic session-identity mapping.** Nothing here maps a `workspace_id` to a `ListAgents`
  identity or a handover slug for you; that correlation is a judgement call.

## 5. Decisions, and the one still open

1. **The spawn witness is events-first, delivery-record-second, running-turn-third, screen-last**
   (`src/cmux/witness.ts`). A pickup queued but not yet CONSUMED is invisible to all four (MEASURED), and a retry makes it
   worse — both sends land, and the duplicate fires as a whole second run when the child's first turn ends.
   So the pickup is sent ONCE, the unwitnessed case is a reported state rather than a failure, and the ask
   lifecycle carries `dispatch-unwitnessed` (holds the burst slot, swept like a running worker, raises no
   `:warning:`, reconciled against `latest_submitted_message` on a later sweep).
2. **OPEN: give the supervisor's sweep (`skills/supervisor/SKILL.md` § 7) an events subscription instead of
   (or ahead of) its fixed 1200s cadence**, narrowing the timer-driven sweep to the jobs events can't do
   (§ 4) while events carry liveness/stuck/waiting in real time. Proposed slug:
   `supervisor-events-driven-wakeups`.
3. **The handover lifecycle publishes no status or checklist** (§ 2(c), the owner's ruling) — a seat's
   state reaches the owner only as a Queue card or a floating note.
