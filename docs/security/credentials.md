# Credentials

Part of [Security & trust](../security.md).

- **No language-model API key at all.** No reasoning session runs on a key this product holds: the transport
  is your existing Claude Code or Codex session, the optional `slopweaver codex` passes reuse the Codex OAuth
  login already in the `auth.json` of the plan home each pass is routed to (see
  [The Codex boundary](codex-boundary.md#the-codex-boundary-slopweaver-codex)), creating and storing nothing, and the
  plan-budget probe of Data flow item 3 spends each Claude plan's own login — the one Claude credential stored
  is a setup token you hand `claude token`, written at `0600` into that plan's store. The console voice runs
  on your ChatGPT plan through the Codex login of the plan home it is routed to, and nothing else (every call rides
  the ChatGPT plans, with no platform.openai usage), so no platform.openai key is stored and a plan
  that refuses a call is a refusal, never a spend. What crosses is
  [The console-voice boundary](voice-boundary.md#the-console-voice-boundary-slopweaver-talk).
- **Connector tokens are yours, and are stored locally.** All optional, each needed only for the source or
  capability you use:

- **The local stack's Storage key is not stored at all.** The service-role key the measurement bucket is
  called with, and the gateway's URL, are read off the RUNNING local stack each time Storage is opened —
  `docker inspect` of the Storage container's `SERVICE_KEY` setting and of the gateway's loopback publication
  (`src/store/objects/selectionCore.ts`) — so no file, store row or backup holds a copy. A gateway published beyond loopback is refused outright.
- **How they are stored.** `slopweaver secrets set <name>` writes to
  `$SLOPWEAVER_HOME/secrets/<name>` with mode `0600`, read from a **no-echo prompt or piped stdin —
  never from argv**, so a token cannot leak into shell history or a process list. A row whose form is
  knowable declares it (`valueShape` on its row, in its category file under `src/secrets/credentials/`), and a
  value that does not match is refused before anything is written, naming the row and never the value —
  an autolinked paste once stored `http://<id>/`. The writer never writes through a symlink, at the secret's
  path or the secrets directory, and refuses a home its group or others can write (`writeSecretFile`,
  `src/secrets/store.ts`). They are marked
  sensitive in the plugin config so they are never printed. Values are stored as-is on your filesystem;
  they are not encrypted at rest, so filesystem access is the trust boundary. **In the BACKUP they are
  encrypted**, under the one master password `backup-passphrase` names — [egress item 13](data-flow.md) above has the whole
  shape and the reason the two answers differ.
- **How a value gets there from the console.** A hand step's queue card draws a secure paste field per secret it
  stores; `POST /api/secret` (`site/app/api/secret/route.ts`) takes the same loopback, same-origin guard as every
  console write and runs that same `secrets set <name> --stdin`, the value on the child's stdin, never its argv. The
  response names the key and the path, never the value, and the console voice has no tool that reaches the route.
  Residue: any process already running as you can call it with the headers the page sends — a local door, not an
  authenticated one ([pasting a secret](../../skills/hand/reference/pasting-a-secret.md)). LOCAL because the console
  listens on 127.0.0.1 only (`console_host` in `scripts/docs-site.sh`): the guard reads headers a client writes, so
  the bind, not the guard, is what refuses another host.
- **How you see what is in there.** `slopweaver secrets status` prints the table above against the files
  actually standing in your store — and **never a value.** That is structural rather than a promise: the
  only file it opens is a `*-oauth.json` grant, and the only fields it takes out of one are the bound
  account, the NUMBER of approved scopes, the scopes that are not provably read-only (a scope URI is a
  public identifier, never token material), and the cached access token's expiry. A single-line secret's
  bytes are never read; its mode and its mtime are. `--json` adds one word beside the rows, `datadogSite`
  (`set`, `unset` or `invalid`, never the site itself): the site is config in `profile.json` rather than a
  secret, and Datadog's two keys reach nothing without it, so the console's Integrations catalog reads it there.

  **A grant's AT MINT label is derived from the scopes on disk**, never asserted: any scope that is neither
  an identity scope nor spelled `.readonly`/`.read-only` makes it `read-write`, an unknown counted rather
  than assumed safe. The register's own value is only the fallback for a file not there to read — an
  asserted label would print `read-only` beside a grant that in fact carries write scopes.

  It leads with what you did not ask for, because the four states it was built to surface had each been
  standing unnoticed until an audit found them by hand: a grant whose cached access token
  has expired (`access-token-expired` — the grant itself is live until revoked, and the next call refreshes
  it), a grant that records no expiry at all (`expiry-unrecorded`), a file nothing in `src/` reads (`dead`),
  and a file the register does not know at all (`off-allowlist` — placed by hand, or written from another checkout whose register carries its row, so
  `secrets set` here would refuse to rewrite it; the `secrets-registry` gate names that branch when one does). A fifth falls out of the same read: a store file whose mode is not `0600`
  (`loose-mode`). A sixth is the register's claim failing against the disk: a grant the register declares
  read-only that carries a scope not provably read-only (`write-scope-on-read-only`), named scope by scope. A
  seventh is a stored grant file that does not parse as a grant (`grant-unreadable`), which its door cannot use,
  and an eighth a single-line secret of zero bytes (`empty`), read off its size and never its contents.
  `--all` adds the rest of the register — the credentials you have not connected, and the
  retired names you have no file for, which is the only way to read the register itself rather than this
  store; `--json` emits every row. The one absent row that is news — a live credential missing while a row
  on its platform is stored, as when a split adds a row nobody set — does not wait for you to run this: the
  `secret-absent` monitor cards it with the `secrets set` command to paste, reading file names only
  ([secret-absent](../../skills/monitor/reference/secret-absent.md)).

  **A verb reporting a missing credential is answered from the store, never from the owner.** Run `secrets
status` before saying a token is absent: the file NAME carries the platform and the contents only the raw
  token, so searching file contents for a service name finds nothing and reads as "no credential" — which is
  how a stored Vanta pair was once re-requested from the owner nine days after it was set. Only a row the store
  genuinely lacks is a gap worth putting to the owner.

- **A credential whose register row has not landed blocks every push on the machine.** `secrets set` run from
  a branch whose register carries a new row writes the file, and the store is shared by every checkout, so
  `secrets-registry`'s `store-unregistered` check — one of the local `pre-push` lane's gates — refuses every
  other session's push until the row reaches `main`. MEASURED: three sessions were refused a push by
  one session's file. The row cannot run ahead on its own either: a `live` row whose `reader` module is not yet
  a tracked source fails `reader-missing`, so the row and its reader land together. Renaming the file does not
  help, since the check reads every file in the directory, dotfiles included. So until the row lands, reach
  the value the way its reader allows without a file — the store, for instance, reads `SLOPWEAVER_STORE_URL`
  before `store-url` — and if a file must exist to exercise a path, delete it in the same turn and prove the
  gate clean with `yarn slopweaver dev lint --only secrets-registry`.

- **Scopes are checked before use.** `slopweaver connect check <source>` preflights a source and reports
  the exact scopes its ingest needs against what your token actually has, including the separate
  write scopes, so you can grant read-only and see precisely what that forecloses.
- **A metrics producer is handed only the credentials its declaration maps.** `datadog produce` runs a command
  `profile.json` `datadog.metricsProducers` declares, with a clean environment: `PATH`, `HOME`, `TMPDIR`,
  `SLOPWEAVER_HOME`, and each `secrets` entry read from the store. A mapped name must be one this register declares,
  so it is a credential `secrets status` already shows; the value travels in the child's environment, never its
  argv, and is never logged. That bounds what is handed over, not what the producer does: it runs as you, so the
  profile naming it is trusted as code ([metrics push](../../skills/automation/reference/metrics-push.md)).
- **The 1Password atlas account is CLI-only — never the desktop app.** The app refuses a second account on
  the same team (only one Acme team account can be signed in at a time),
  and with its CLI integration on, `op` reads accounts from the app, so the standalone `atlas` account in
  `~/.config/op/config` vanishes from `op account list`. `OP_BIOMETRIC_UNLOCK_ENABLED=false` switches `op`
  back to that file, and every `op` call `slopweaver onepassword sync` makes carries it and `--account atlas`
  (`ONEPASSWORD_ACCOUNT` names another shorthand), so a session for any other account is never synced. By hand, in a
  terminal: `OP_BIOMETRIC_UNLOCK_ENABLED=false op account list` shows `atlas`, then
  `eval "$(OP_BIOMETRIC_UNLOCK_ENABLED=false op signin --account atlas)"` with the dedicated account's
  password. Unattended, the sync does the same from `onepassword-atlas-password`: `op` reads a password
  only from a terminal, so `/usr/bin/expect` gives it one and types the password after the prompt (never
  an argv, never echoed), and the session token lives only in the environment of that run's own `op` calls.
